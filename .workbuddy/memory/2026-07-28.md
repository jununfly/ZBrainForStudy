## libsql FFI flake 加固（推广加锁到所有 libsql 集成测试）
- 背景：Windows 下 `cargo test` 驱动 libsql 原生 FFI 会随机 `STATUS_ACCESS_VIOLATION` (0xc0000005)；1-1-2 时 `extract_atoms.rs` 用进程级 `OnceLock<Mutex<()>>` 锁串起本文件测试（当时 4/4 稳定）。
- 本次把同一锁模式推广到 `crates/zbrain-core/tests/` 下全部 51 个引用 `LibsqlEngine` 的集成测试文件（`extract_atoms.rs` 已有锁，跳过）：
  - 每文件加 `static LIBSQL_TEST_LOCK: std::sync::OnceLock<std::sync::Mutex<()>>` + `fn libsql_test_guard()`，每个 `#[tokio::test]`/`#[test]` 函数体首行 `let _guard = libsql_test_guard();`。
  - 用脚本 `.workbuddy/_tmp_add_guard.py` 机械插入（插入点：最后一个顶层 `use` 之后；guard 行插在函数体 `{` 之后第一行）。修复 `takes_crud.rs` 因多行 `use {..}` 被插断的编译错误。
  - 各测试二进制内串行、二进制间仍并行（FFI 崩溃是进程内多线程问题，跨进程独立）。
- **关键发现（重要）**：锁只是「部分缓解」，并**不能**根治 flake。对最易崩的 `extract_facts`（6 tests）做了 4 组各 ×3 运行验证：
  1. 仅 body-mutex 锁（默认并行）→ 仍崩
  2. `#[tokio::test(flavor="current_thread")]` + 锁（默认并行）→ 仍崩
  3. `--test-threads=1`（单线程 harness）→ 仍崩（3 次中 2 次崩）
  4. 泄漏 temp 文件（排除删文件竞态）→ 仍崩
  ⇒ 这是 **libsql/SQLite 原生 FFI 在 Windows 上的真·间歇性崩溃**，与测试并发/文件生命周期无关，代码层无法根除。
- **可靠绿的唯一路径在基础设施层**：CI 对 libsql 集成测试 (a) segfault 重试，或 (b) 跑在 Linux/macOS agent。代码层锁保留作为降低频率的缓解（且是用户要求的「推广加锁」动作），但不可承诺稳定全绿。
- `cargo test -p zbrain-core --no-run` + 抽跑确认：51 文件全部编译通过（仅既有 warning，无 deny(warnings)）。
