## 诊断：PGLite initSchema() 挂死的根因（重要纠正）

此前误判为"本机 PGLite initSchema 挂死 = 环境预存问题"。实测**不是 PGLite 问题**，是**代码 bug**：
- 隔离复现：`CREATE EXTENSION vector` / pg_trgm / 建表 / HNSW 索引 / vector 插入全部 <1s，PGLite 原语都快。
- **真正根因 = 无限递归**：`PGLiteEngine.initSchema()`（pglite-engine.ts:312/317）调 `runMigrations(this)`；`runMigrations`（migrate.ts:26）无条件 `await engine.initSchema()`。两者 async 互相调用、无 guard/终止条件 → `initSchema→runMigrations→initSchema→…` 永不返回。因 async 每次 await 后栈帧回收，不栈溢出，只超时（90s）。插桩确认循环：`before runMigrations` 之后立刻又 `before applyForwardReferenceBootstrap`。
- **回归来源**：Rust 迁移 "HARD CUTOVER" 把 `migrate.ts` 改成 100% 委托 `engine.initSchema()`（此前 runMigrations 有自有迁移逻辑、不回调 initSchema，无环）。`initSchema` 里的 `const { applied } = await runMigrations(this)`（:317）是冗余且闭环的那一行——且 runMigrations 永远返回 `{applied:0}`（迁移现全在 Rust），删掉这行即可破环。
- 顺带发现的 PGLite 平台怪象（非挂死原因、是红鲱鱼）：本机 Windows PGlite 的 `information_schema.tables` 对**全新库也把每张表都报成 exists**（探针全 true），导致 `applyForwardReferenceBootstrap` 误判为 Pre-v0.21 脑。这是 PGLite 在此平台的信息模式假阳性，与递归无关。
- **影响**：任何机器只要跑到 `PGLiteEngine.initSchema()` 都会死循环；此处被 `oauth.test.ts` / `operations-trust-boundary.test.ts` 的 `beforeAll` 踩中。
- **已修复（2026-07-22，方案1 拆环·删自调用）**：删 pglite-engine.ts 与 postgres-engine.ts 两个 `initSchema` 里的 `const { applied } = await runMigrations(this)` 及其死分支（applied 恒为 0）；同时移除两引擎 `import { runMigrations }`（已无调用者）。`runMigrations`（migrate.ts）保留为指向 `initSchema` 的薄委托——至少 8 个 tests/benches 仍依赖它，不能删。单向依赖：委托调权威，权威不再回拨。两处补注释说明防复发。
- **验证**：真实 `runMigrations(engine)` 532ms 返回、`initSchema()` 116ms 返回、query 正常、EXIT=0（此前会无限递归超时）；`operations-trust-boundary.test.ts` 14 pass / 0 fail / 2.95s（此前卡死）。改动纯 TS，未动 Rust，无需重跑 Rust 三道门。
