### CRLF 惨痛教训（必须记）
用 Python 脚本往 CRLF 的 `lib.rs` 插大块代码时，**脚本用了 replace（替换锚点）而非 insert（保留锚点）**，把 5 处既有代码整个覆盖删掉：`EvalCrossModal` 枚举变体、`EvalCrossModalArgs` 的 `json` 字段+结构体闭合 `}`、dispatch 臂、`run_eval_cross_modal_command` 函数尾（`std::process::exit(code);`+`}`）、`read_code_retrieval_report` 签名、既有测试 `eval_cross_modal_is_no_longer_an_unported_subverb`。症状：编译器报 unclosed delimiter 指到不相关 opener，逐处 whack-a-mole 修。
**正确做法**：`git checkout HEAD -- <file>` 还原干净，再用**纯 insert** 脚本（anchor 内容保留，只在前后加内容）干净重做。校验：用带 lifetime 处理的括号扫描器确认 depth=0；`git diff --numstat --ignore-space-at-eol` 看真实改动（本仓 `core.autocrlf=true` 且 HEAD 部分文件存 LF，普通 numstat 对 CRLF 文件是行尾假阳性，忽略行尾才见真实 286 added/0 deleted）。

## git 对象库损坏诊断（22:xx，clone 是否能根治）

推送 `ca5ad2c2` 后 `git status` 显示 rust-rewrite ahead 182（假象）——根因是本地仓库对象库有坏对象，触发自动 gc/几何 repack 失败（`bad tree object 0e0d0a2d`），把 `origin/rust-rewrite` 跟踪引用反复回滚到旧值 `31f4a8ad`。`update-ref`/`fetch` 写回后被失败 repack 覆写。

- **诊断命令与结论**：
  - `git cat-file -t 0e0d0a2d...` → `fatal: could not get object info`（缺失，非损坏）。
  - `git fsck --connectivity-only` → missing tree `0e0d0a2d` + missing blob `0c133629`/`0925c7a2` + missing tree `028076ca`，均挂在几个老 tree 的 broken link；HEAD/`refs/heads/rust-rewrite` **reflog 有 invalid entry `82b34936`**（reflog 损坏，可丢）。
  - `git rev-list --all | grep 0e0d0a2d` = **0**（坏对象不可达于任何当前 ref，含 `ca5ad2c2` 历史）。
  - `git ls-remote origin rust-rewrite` = `ca5ad2c2`（origin 健康，push 成功）。
- **结论**：坏对象全部不可达，属本地对象库丢失的残留；origin 完整。**重新 clone 能从根解决**（clone 从 origin 取完好对象，或根本不带不可达残留），不丢代码（`ca5ad2c2` 已在 origin）。
- **执行前必须备份的未提交内容**（clone 到新目录会丢）：`engine.rs`（428 行 find_trajectory WIP，未提交）、`.tmp_ts_src/`、` .workbuddy/memory/2026-08-10.md`。
- **铁律**：严禁 `git stash`（触发 .git/refs cleanup）；备份用 `cp` 到仓库外。clone 用 `git -c gc.auto=0 clone <url> <new-dir>` 避免克隆后立即 repack 又撞坏对象（虽然新仓库无坏对象，加上无妨）。
